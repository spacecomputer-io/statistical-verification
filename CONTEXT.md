# Project Context

Rust library providing bindings for two statistical RNG test suites: **TestU01** and **PractRand**. Any type implementing `RngCore` can be tested.

## Architecture

- `src/lib.rs` — Re-exports `testu01` and `practrand` modules behind cfg flags
- `src/testu01.rs` — FFI bindings to the C TestU01 library. Uses a global `Mutex<Option<RngAdapter>>` to bridge Rust's `RngCore` trait to TestU01's C callback (`extern "C" fn`). Bindings are auto-generated by `bindgen`
- `src/practrand.rs` — Spawns the `RNG_test` binary as a subprocess, pipes random bytes to its stdin, and parses the exit code. No FFI involved
- `build.rs` — Downloads, compiles, and installs both TestU01 (C, autotools) and PractRand (C++, manual g++ compilation) into `vendor/`. Sets cfg flags `has_testu01_bindings` and `has_practrand`

## Build

The build script automatically downloads and compiles the C/C++ dependencies on first build. Requires: Rust toolchain, C/C++ compiler (gcc/g++), `make`, `curl`, `tar`, `unzip`.

```bash
cargo build        # downloads + compiles vendored C/C++ deps on first run
cargo test         # runs smoke tests (SmallCrush for TestU01, 1MB for PractRand)
```

The `vendor/` directory is gitignored — it's created at build time, not checked in.

## Key design decisions

- **TestU01 uses FFI** because it needs a C function pointer callback to pull random data. The global mutex is required because TestU01's callback signature has no user-data parameter
- **PractRand uses subprocess** because it's simpler — the `RNG_test` tool reads from stdin, so we just pipe bytes to it
- **Conditional compilation** (`#[cfg(has_testu01_bindings)]` / `#[cfg(has_practrand)]`) — modules are only available when their C/C++ deps compiled successfully

## Tests

- `tests/testu01_test.rs` — Runs SmallCrush on `OsRng`
- `tests/practrand_test.rs` — Runs PractRand on `ChaCha20Rng` with 1MB of data

Tests are slow (SmallCrush takes ~30s, PractRand is faster at small sizes). Both are gated behind cfg flags.
